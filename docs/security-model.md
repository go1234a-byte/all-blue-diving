# 보안 모델 (RLS 기준, 실제 적용된 정책)

Supabase Row Level Security를 쓴다. 클라이언트에는 **anon 키만** 넣는다. `service_role` 키는 앱과 웹에 넣지 않는다.

## 역할별 권한

| 테이블 | 다이버 (본인) | 강사 (본인 투어) | 관리자 |
|---|---|---|---|
| bookings | 본인 예약 읽기 (기존 정책) | 본인 투어 예약 읽기 (기존) | 전체 (기존) |
| tour_dive_plans | 본인이 예약한 투어의 계획 읽기 | 본인 투어 계획 읽기·쓰기 | 전체 읽기·쓰기 |
| tour_change_log | 본인이 예약한 투어의 변경 이력 읽기 | 본인 투어 이력 읽기 | 전체 읽기 |
| devices | 본인 기기 읽기·추가·수정 | - | - |
| dive_logs | 본인 기록 읽기·추가·삭제 (수정 정책 없음) | 조회 불가 | 조회 불가 (정책상) |

## 검증한 것 (운영 DB, 롤백 트랜잭션, 실제 사용자 역할로 실행)
- 다른 사용자의 `user_id`로 기기 등록 → **차단됨**
- 다른 사용자의 `user_id`로 기록 추가 → **차단됨**
- 다른 다이버의 예약 `booking_id`를 기록에 연결 → **차단됨**
- 다른 사용자의 기록 조회 → **0건 (보이지 않음)**
- 본인 기기 등록 → 허용

## 원본 불변
- `dive_logs`에는 수정 정책이 없다. 삭제는 본인 기록만 가능하다 (`dive_logs_delete_own`, 마이그레이션 `20261003020000`).
- 서버에서 지워도 아이폰 로그북의 원본은 그대로 남는다. 서버 사본만 지워진다.
- 사용자 메모 같은 주석은 별도 테이블로 분리하는 것을 P2에서 검토한다.

## 주의
- 투어 앱 일부 테이블 정책은 예전 구조(`bookings_public_update using (true)`)가 남아 있었다가 `20260812020000`에서 잠갔다. 새 정책 작성 전에 기존 정책을 항상 확인한다.
- 마이그레이션 기록이 로컬과 운영 사이에 어긋나 있다. `db push`를 쓰면 안 된다. 적용은 파일 단위로 `db query -f` 후 `migration repair`로 기록한다.
